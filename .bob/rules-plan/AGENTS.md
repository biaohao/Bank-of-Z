# AGENTS.md — Plan Mode

This file provides architectural constraints for AI agents planning changes in this repository.

## Schema Change Impact Map

Any change to the `CUSTOMER` DB2 table or its copybooks is a **cross-cutting concern** affecting 8+ layers:

```
DB2 DDL (CUSTOMER table)
  └─ CUSTDB2.cpy (DECLARE TABLE)
  └─ CUSTOMER.cpy (COBOL struct)
  └─ CRECUST.cpy / INQCUSTZ.cpy / UPDCUST.cpy (COMMAREAs)
       └─ CRECUST.cbl / INQCUST.cbl / UPDCUST.cbl (business logic + SQL)
            └─ BNK1CCS.cbl (inline SUBPGM-PARMS — NO COPY)
            └─ BNK1DCS.cbl (inline WS-COMM-AREA + DFHCOMMAREA — NO COPY)
            └─ BNK1CCM.bms / BNK1DCM.bms (BMS screen fields)
  └─ z/OS Connect provider .cpy files (regenerated, not source-edited)
       └─ Mapping YAMLs (operations/*.yaml)
            └─ openapi.yaml (API schema)
                 └─ src/frontend/ (Web UI)
```

**Critical architectural risk**: `BNK1DCS.cbl` and `BNK1CCS.cbl` do NOT use COPY for their COMMAREA definitions — they have inline duplicates. These are the highest-risk files for silent COMMAREA size mismatches.

## Build Sequencing Constraint

BMS assembly **must precede** COBOL compile for `BNK1CCS` and `BNK1DCS` because they COPY the BMS-generated symbolic map. DBB handles this automatically; do NOT propose build changes that decouple BMS from COBOL compilation.

## DB2 Change Ordering

1. `ALTER TABLE` DDL **before** DBRM bind — column must exist before bind executes
2. DBRM bind for each affected program into plan `BANKZPLN`
3. Wazi Deploy → CICS load library
4. z/OS Connect provider `.cpy` regeneration **after** COBOL load is deployed (CLI introspects running program)
5. z/OS Connect API DBB build + Wazi Deploy

## IMS vs CICS Path Isolation

IMS and CICS paths are **architecturally isolated** — they share no copybooks and no programs. Changes to CICS customer handling have zero impact on IMS programs and vice versa. The only shared layer is the z/OS Connect OpenAPI spec (`openapi.yaml`) and the Web UI routing logic.

## z/OS Connect Provider Files

Provider `.cpy` files in `gen/` are **not source** — they are build artifacts generated by the z/OS Connect CLI by introspecting a running COBOL program. Any plan that modifies them directly is incorrect. The correct plan is: deploy COBOL → regenerate via CLI.

## Deployment Libraries

| Source type | Deploy target library |
|---|---|
| CICS COBOL | `CICSLOAD` |
| IMS COBOL | `IMSLOAD` |
| Batch COBOL / PL/I | `LOAD` |
| IMS PSB Assembler | `PSBLOAD` |
| IMS DBD Assembler | `DBDLOAD` |
| IMS Java JAR | IMS Java classpath USS directory |
| z/OS Connect API | Liberty WAR on USS |
| Web UI WAR | Liberty WAR on USS |

## Bottleneck: SORTCODE.cpy

`SORTCODE.cpy` is included by virtually every CICS program (~21 programs). A change to this copybook triggers a full CICS layer rebuild. Plan for extended build time if this copybook must change.

## Agent Planning Artifacts

Store structured planning output under `bobz/`:
- `bobz/impact-analysis/<feature-name-YYYYMMDDTHHMMSS>/IMPACT-ANALYSIS.md`
- `bobz/implementation-plans/<feature-name-YYYYMMDDTHHMMSS>/implementation-plan.md`

This directory is agent-writable and excluded from application builds.
