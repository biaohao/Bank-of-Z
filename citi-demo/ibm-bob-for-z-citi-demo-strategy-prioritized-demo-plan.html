What you are working with — critical for demo preparation and for Citi's credibility assessment.

40+COBOL programs (CICS + IMS)
2PL/I programs (Batch & IMS)
9IMS DBDs (HLASM)

CICS Path (customer ID: C####)

  • BNKMENU — main menu, ~42KB
  • CRECUST — create customer, ~58KB, 1,631 lines — calls 5 async credit agency programs (CRDTAGY1–5), enqueues named counter, writes PROCTRAN
  • INQCUST — customer inquiry, 785 lines, CICS+SQL
  • UPDCUST / DELCUS — update/delete customer
  • CREACC / INQACC / INQACCCU / UPDACC / DELACC — account CRUD
  • DBCRFUN — debit/credit, 861 lines — reads ACCOUNT from Db2, writes PROCTRAN
  • XFRFUN — funds transfer, 1,924 lines — most complex program; reads two accounts, updates both, writes PROCTRAN, handles MQ external transfer
  • BANKDATA — batch data init, 1,897 lines, SQL-heavy

IMS Path (customer ID: I####)

  • IBLOGIN1 / IBLOGOUT — IMS session control
  • IBGCUDAT / IBSCUDAT — get/set customer data via IMS DB
  • IBACSUM — account summary
  • IBTRAN — IMS transaction processing
  • LOADCUST / LOADACCT / LOADHIST — IMS data loaders
  • IBLOGIN.pli — PL/I IMS login program
  • 9 IMS DBDs in HLASM: CUSTOMER, ACCOUNT, CUSTACCS, HISTORY, TSTAT…

Batch / PL/I

  • BNKSTMT.pli — 29,750 byte PL/I bank statement generator, JCL-driven
  • BNKSTMT.jcl — batch job control

Architecture Stack — Directly Maps to Citi's Real Environment

  • API Gateway: z/OS Connect exposing REST APIs — CRECUST, INQCUST, UPDCUST, INQACC, DBCRFUN, XFRFUN, IBACSUM, IBGCUDAT, IBSCUDAT, IBTRAN (10 z/OS assets defined)
  • Transaction middleware: Both CICS (online banking) and IMS TM (core banking) — dual-path routing by customer ID prefix
  • Databases: Db2 (CUSTOMER, ACCOUNT, PROCTRAN tables) + IMS DB (hierarchical databases for IMS path)
  • Async messaging: IBM MQ for external bank-to-bank transfers (XFRFUN ↔ Bank of Q)
  • Toolchain: .bob config, dbb-app.yaml (DBB build), zapp.yaml (Z application), zcodescan/ (security scan), Zowe CLI, GRUB, VS Code, DBB pipeline
  • DevOps: Pre-commit hooks (.pre-commit-config.yaml), detect-secrets, renovate.json (dependency scanning), docker-compose.yaml
Demo credibility note: This is not a toy app. XFRFUN alone is 1,924 lines with multi-account Db2 updates, MQ integration, PROCTRAN writes, and full error rollback. CRECUST orchestrates 5 async CICS programs with credit agency aggregation. This closely mirrors the complexity Citi's teams face daily.

The Devin Situation — What It Means for This Demo

Citi's teams use Devin for general development workflows. This creates three distinct dynamics you must address:

  • Comfort: They know what autonomous agent-style AI feels like. Do not re-explain the concept — jump straight to Z-specific differentiation.
  • Risk: "We already have Devin, why do we need another tool?" must be pre-empted with concrete, Z-specific demo moments where Devin would fail or hallucinate.
  • Opportunity: Positioning coexistence ("Devin for your Java microservices, Bob for Z for your mainframe core") removes the replace-vs-add-cost objection and widens adoption surface.

The demo's single most important moment: Show Bob for Z producing a correct, Z-aware answer — ideally with IMS/CICS/Db2 context — where Devin would have no choice but to guess.

3. Prioritized Demo Scenarios

Ordered by business impact and differentiating power. Aim to cover P1–P3 in a focused 60–90 minute demo. P4 is optional depth for technical audiences.

1

Enterprise-Wide Impact Analysis — "What breaks if I change this?"

P1 — Must Show SDLC: Plan / Architect Devin differentiator

Scenario: Citi's Wealth team needs to add a new email field to the customer record (Bank of Z's exact CICS enhancement tutorial). Ask Bob in Z Architect mode: "I need to add an email address field to the customer data model. What is the full impact across the Bank of Z application?"

What Bob for Z shows:

  • Traverses all 40+ COBOL programs using application metadata — not just the open file
  • Identifies every program that COPYs CUSTOMER.cpy, CUSTDB2.cpy, or INQCUSTZ.cpy
  • Flags impact on: CRECUST, INQCUST, UPDCUST, DELCUS, BNK1CCS (the customer create screen BMS map), CUSTMAP.cpy, the z/OS Connect INQCUST/UPDCUST/CRECUST API assets, and the Db2 CUSTOMER table
  • Produces a prioritized implementation checklist

Why Devin cannot match this: Devin would analyze only files in its retrieval window. It has no persistent application model. For a codebase with 40+ programs and 38 copybooks, it would miss cross-file copybook dependencies, Db2 table schema alignment, BMS map fields, and z/OS Connect COMMAREA structures — all of which must change together. A missed dependency in a banking system is a production incident.

Citi resonance — Custody & Wealth: Changing a data field in a settlement or card system and missing one downstream program is exactly how production incidents happen. The metadata-driven impact analysis is the single most risk-reducing capability in the deck.

2

End-to-End Enhancement — Plan → Code → Build → Validate

P1 — Must Show SDLC: Full cycle

Scenario: Continue from scenario 1. Add the email field end-to-end using the CICS enhancement tutorial that ships with Bank of Z. This is a ready-made, rehearsed demo path.

What to show:

  • Plan: Bob generates the implementation checklist from impact analysis (which files to change, in which order)
  • Code — CUSTOMER.cpy: Bob generates the COBOL copybook addition for CUSTOMER-EMAIL PIC X(100)
  • Code — CUSTDB2.cpy: Bob updates the Db2 host variable copybook
  • Code — CRECUST.cbl: Bob adds email to the data flow through CRECUST's 1,631-line program, knowing the program's structure (COMMAREA, credit agency calls, PROCTRAN write) from the metadata — not just from what is visible on screen
  • Code — INQCUST.cbl / UPDCUST.cbl: Bob applies consistent changes using enterprise coding standards
  • Code — BMS map (BNK1CCA.bms or similar): Bob adds the email field to the CICS screen definition — a capability Devin has zero context for
  • Build: Trigger DBB build pipeline — dbb-app.yaml — show incremental build and deployment
  • Validate: Open Bank of Z web UI, create a customer with email, verify end-to-end

This is the Bank of Z tutorial video scenario — a pre-built, battle-tested demo flow with reference videos already available at the Bank of Z GitHub releases.

  • Cross-reference to SORTCODE.cpy, XFRFUN.cpy, ACCDB2.cpy, PROCDB2.cpy dependencies

Devin contrast moment: Ask Devin the same question. Its context window will ingest the 1,924-line file but will lack: (1) the copybook definitions for SORTCODE, ACCDB2, PROCDB2, XFRFUN.cpy, (2) the CICS SYNCPOINT semantics, (3) the PROCTRAN table schema, (4) the MQ configuration. Bob for Z has all of this through application metadata.

CRECUST Credit Agency Refactoring — Async CICS Pattern

P2 — High Value SDLC: Refactor / Code Devin differentiator

Scenario: CRECUST calls 5 credit agency programs (CRDTAGY1 through CRDTAGY5) asynchronously via CICS START, waits 3 seconds, and aggregates the credit scores. Ask Bob: "CRECUST is calling 5 credit agency programs with a fixed 3-second wait. Refactor this to use CICS RETRIEVE-SUBEVENT to wait for all responses before proceeding, and add a 6th credit agency CRDTAGY6."

What Bob for Z shows:

  • Understanding of the existing CICS asynchronous API pattern — not guessing from generic COBOL knowledge
  • Generating CICS RETRIEVE-SUBEVENT logic that correctly integrates with the existing COMMAREA structure
  • Creating CRDTAGY6.cbl consistent with the pattern in CRDTAGY1-5
  • Updating the aggregation logic without breaking existing credit score handling
  • Z-specific guidance: using IBM-curated CICS standards rather than generic patterns that may not compile on z/OS

Wealth (Cards) resonance: Card onboarding and credit decisioning use exactly this pattern — multiple async bureau calls, aggregation, decision. Bob for Z's deep CICS knowledge is a direct accelerator.

PL/I Batch — BNKSTMT Statement Generator

Devin contrast: Devin will produce a surface-level attempt with high hallucination risk on PL/I syntax — especially PL/I's ON conditions, BASED variables, and z/OS I/O patterns. Bob for Z's IBM-curated PL/I RAG produces correct, compilable PL/I aligned to IBM PL/I Enterprise Edition standards.
